2025 年 11 月，Inkwell 的线上首屏要加载 214 KB 的 JavaScript。这个数字不算离谱——大多数 Markdown 编辑器都在这个量级——但它意味着在 4G 网络下，用户在看到第一个字符之前要等 2.8 秒。

我给自己定了一个预算：48 KB，gzip 后，包含所有首屏必需的代码。选 48 而不是 30，是因为编辑器内核（CodeMirror 6 的 language 包加上状态管理）单独就有 41 KB，硬压到 30 只会逼我做假优化——比如把代码挪进 `vendor.js` 然后假装它不存在。

## 先测量，再动手

大多数人优化性能的第一步是打开 bundle analyzer，然后开始删依赖。这个顺序是错的。分析器告诉你代码有多大，但不告诉你哪一部分在关键路径上。

我用三个数字：LCP、INP，以及「首次可交互的字节数」——从 HTML 开始下载到主线程第一次空闲期间，浏览器实际解析并执行了多少 JS。第三个数字最容易被忽略，也最能解释「为什么我的 bundle 只有 60 KB，LCP 还是 3 秒」这种困惑。

测量结果是：214 KB 里，有 **96 KB 是首屏完全用不到的**——PDF 导出、图床同步、设置面板，以及一个完整的 i18n 词库。

> 性能预算不是「尽量小」，而是一个你必须能说清楚来源的数字。说不出来源的预算，最后一定会被「就加一个小功能」突破。
>
> —— 我写在项目 README 第一行的话

## 三条取舍

1. **用动态 import 切开非关键路径**，但只在真正需要时触发。PDF 导出改成点击时加载，代价是首次导出多 300ms，换来首屏少 96 KB。
2. **放弃全量 i18n**。中文和英文两套词库改成按 locale 分包，首屏只加载当前语言，词库从 34 KB 降到 7 KB。
3. **把设置面板的默认状态改成纯 CSS 渲染**，JS 只在用户真正打开时才挂载。这一步最难，因为它要求我承认：大部分用户从来不打开设置。

第三条听起来像偷懒，但它其实是最诚实的优化：把一个默认关闭的功能从关键路径上摘掉，不需要牺牲任何体验。

## 结果

首屏 JS 从 214 KB 降到 48 KB，LCP 从 2.8s 降到 1.1s。INP 保持在 80ms 左右——因为这个指标本来就没什么问题，我也没有为了它做额外的事。

更重要的是，这个预算现在是 CI 的一部分。size-limit 在每次 PR 上跑，超过 48 KB 就失败。规则写进流水线之后，就不会再有人「顺手加一个小功能」了。

## 一点反思

做完之后我意识到，214 KB 里有 96 KB 不是「性能问题」，是「产品问题」——它们是被默认打开的功能带进来的。性能优化的尽头，往往是在问：这个功能真的需要在首屏吗。
